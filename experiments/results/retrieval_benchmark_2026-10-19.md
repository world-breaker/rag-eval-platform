# 检索基准：质量 + 延迟（全档位对照）

- 生成日期：2026-10-19
- 环境：Python 3.12.9 / torch 2.14.0+cu132 / GPU NVIDIA GeForce RTX 5060 Laptop GPU
- 口径：**文档级** Recall@3 / Recall@5 / MRR（`evaluate_retrieval_doc_level`）
- 延迟口径：单次 `_retrieve`（改写 + query 编码 + 检索 + 重排），**不含生成回答**；
  冷启动 = 切档位后第一次查询（含懒加载与 CUDA 预热），热启动 = 之后所有查询的 p50/p95/均值。
- 热启动重复轮数：普通档位 5 轮，LLM 改写档位 2 轮（生成昂贵）
- 重排模型：`cross-encoder/mmarco-mMiniLMv2-L12-H384-v1`（多语言 Cross-Encoder，本地缓存=True）
- 改写 LLM：`Qwen/Qwen2.5-1.5B-Instruct`（本地缓存=True）

## 结论（基于上表实测）

### realistic

- 纯向量：R@3=1.0, MRR=0.9286, 热 p50=0.62ms
- 混合 RRF：R@3=1.0, MRR=0.9286, 热 p50=2.38ms → ΔR@3=+0.0, ΔMRR=+0.0
### near_dup_stress

- 纯向量：R@3=0.625, MRR=0.4792, 热 p50=0.4ms
- 混合 RRF：R@3=1.0, MRR=0.7708, 热 p50=0.43ms → ΔR@3=+0.375, ΔMRR=+0.2916

### 重排 vs 查询改写：代价换到了什么

| 数据集 | 档位 | ΔR@3 vs hybrid | ΔMRR vs hybrid | 热 p50 vs hybrid |
|---|---|---|---|---|
| realistic | 混合 + Cross-Encoder 重排 | +0.0 | +0.0714 | ×417.9 |
| realistic | 混合 + multi-query 改写 | +0.0 | +0.0238 | ×676.3 |
| realistic | 混合 + HyDE 改写 | +0.0 | +0.0 | ×5306.8 |
| near_dup_stress | 混合 + Cross-Encoder 重排 | +0.0 | +0.2292 | ×172.7 |
| near_dup_stress | 混合 + multi-query 改写 | +0.0 | +0.0625 | ×2788.2 |
| near_dup_stress | 混合 + HyDE 改写 | -0.25 | -0.0333 | ×12951.3 |

读法：重排与改写都是**拿延迟换排序**的可选档位，且换到的收益随语料变化极大——
重排只在排序还有提升空间时有效（召回已满分时它顶多纠正顺序，见上表 ΔMRR）；
而改写（尤其 HyDE）的收益**依赖 LLM 生成质量**：小模型生成的假想文档可能夹带噪声，
在噪声库上甚至会让召回**变差**（上表中出现负的 ΔR@3 就是这种情况）。
这也是本项目把它们做成「默认关、按场景开」而不是默认路径的直接依据：
收益不确定而代价确定（延迟 ×百倍），默认开等于让所有查询为大模型的不确定性买单。

**什么时候有用、什么时候没用**：
1. 干净、话题区分度大的小库上，强向量模型已接近天花板（R@3=1.0），混合检索只能改善**排序**（MRR）而不能改善召回——收益有限，却多了 BM25 的维护成本。
2. 含近义/重复文档的噪声库上，纯向量会把相似度分数摊到多个近义副本上导致正排不上；BM25 的精确词匹配能把「唯一标识该文档的关键词」那一路顶上来——这是混合检索真正的价值区间。
3. 延迟上，BM25 一路是**纯 NumPy、微秒级**，在总延迟里几乎看不见；真正把单次查询从毫秒级拉到秒级的是**查询改写**（要跑 LLM 生成）与**重排**（要对 top-N 逐对过一遍 Cross-Encoder）。所以「默认关、按场景开」不是保守，而是把代价花在有收益的地方。
